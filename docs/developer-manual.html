1Design principles that constrain the code

These come from the plan's decision log (D1 to D16). The code enforces most of them; a change that breaks one is a design change, not a bug fix.

D3Polling intake, no inbound network. The container publishes no ports. Everything starts with a Jira query once per AINS_POLL_SECONDS. Jira Automation and GitHub repository_dispatch are audit conveniences, never triggers.
D4Subscription only. Agents authenticate with CLAUDE_CODE_OAUTH_TOKEN from claude setup-token. minimal_env() strips every ANTHROPIC_* variable and the config schema refuses to pass one through. There is no Anthropic SDK dependency anywhere.
D14One harness, one process per stage. The orchestrator never calls a model. It spawns claude -p with a rendered prompt on stdin and reads one JSON result. Stages are spec, plan, implement, review. The orchestrator commits and pushes; agents may not.
D9Five switchable gates. A gate that is off is passed by the orchestrator with a Jira comment. A gate that is on waits for a human signal in Jira (status), on the PR (label or review) or in Actions (environment approval).
D13The platform is never a target. The platform repo has no CI and no Jira project; it is built from the workstation. Targets are onboarded projects only.
D16The sandbox is permanent. niloyray/ains-sandbox with Jira AINSSB is the regression target for every platform change.

5The poll cycle

ains poll loops forever: run one cycle, sleep AINS_POLL_SECONDS, repeat. One cycle is deliberately small so that a crash or restart loses at most one transition, and so that the event log reads as one line per decision.

  1. Claim. JQL project in (<targets>) AND labels = ai-native AND status = Ready. For each hit without an active session the target's FlowEngine.claim() creates the session (stage spec), moves the story to Specifying and records claimed. A hit whose session is blocked is a human resume: the poller computes the stage to resume at from the event history and sets it.
  2. Step. For every session not in released, abandoned, blocked or pr_reviewed, call engine.step() once. One call performs at most one transition: run an agent and commit, or check a gate, or merge. Errors are caught per session and reported in the cycle line, never propagated.
  3. Watch. PRWatcher.cycle() lists open PRs carrying review_label in each target, skips PRs that belong to a story session, and reviews each new head SHA once, recording a pr-review session.
  4. Report. One log line: cycle: claimed=[...] stepped={KEY: new_stage} skipped=[...] reviewed=[...] errors=[...]. This line is what the monitors and the implementation log quote.

A per-target lock prevents two cycles from stepping the same target concurrently; the poll loop is single-threaded anyway, but session advance from the CLI can run alongside.

Before every cycle the loop re-reads the mounted config (reload_config()): a target added with ains target add is polled on the next cycle without a restart; a config that fails to parse is logged and the last good one stays in force. Jira's search index lags a freshly created issue by several minutes, so "claimed within a minute" holds for stories moved to Ready, not for ones created seconds earlier.

Agent failures: _retry_or_block allows attempts < max_attempts (2) retries with the agent template's back-off, then blocks. On resume, a stage whose output files already exist (STAGE_OUTPUTS) skips the agent and only commits, so a crash between agent and push does not pay for a second run.

Errors while waiting at a gate never behave like agent failures. Waiting is idempotent, so an error from Jira or GitHub at a wait_* stage is recorded as a wait.error event and the stage is kept. Outages (is_transient(): network errors, HTTP 502/503/504, timeouts) are never counted, however long they last; any other error (a deleted PR, bad credentials) counts in attempts and blocks the story after MAX_WAIT_ERRORS (10) in a row. This came out of the sandbox run: one GitHub 503 blocked a story that was waiting for a label.

The story branch is shared with people. Workspace.ensure runs sync_branch before every stage (fetch and checkout -B on the remote tip), so a commit a person pushed while the story waited at a gate is built upon rather than overwritten. A push while a stage runs still collides; the user guide tells people to push only at a wait stage.

7Persistent state

Everything durable lives under AINS_DATA_DIR (/data, volume ains-data): sessions.sqlite (WAL mode, two tables), heartbeat.json (the last cycle report, written by the poll loop and read by the portal and ains status) and logs/orchestrator.log (rotating, 5 × 5 MB, the same lines as the container's stdout). Story clones live under AINS_WORK_DIR (/work, volume ains-workspaces) and are deleted after the merge. data_dir() in cli.py resolves the directory, defaults it to the work dir for older setups, and migrates an existing store from the work volume once. ains-platform.cmd backup copies the data volume to backup/data-<stamp> with docker cp. A bind mount was rejected for the database on purpose: SQLite locking over Docker Desktop's Windows file sharing is unreliable; a named volume with a copy-out command is safer.

9The agent runner

  1. Render the stage template with the story context; append rework text if gate_state.rework_<stage> is set.
  2. Build argv from the template command plus --permission-mode, --max-turns, and for read-only stages --disallowedTools Edit,Write,MultiEdit,NotebookEdit,WebFetch,WebSearch. The prompt goes through stdin, never argv (an earlier version lost the prompt to option parsing).
  3. Build the environment with minimal_env(): base keys (PATH, HOME, locale) plus env_passthrough; raise if anything starts with ANTHROPIC_; refuse to run without CLAUDE_CODE_OAUTH_TOKEN.
  4. Trust the workspace: write the project path into ~/.claude.json so the repo's .claude/settings.json allow list is honoured (headless runs ignore it otherwise).
  5. Run with the wall-clock limit; kill on timeout. Parse the single JSON object (or the last result message of an array) into AgentResult: ok, text, turns, cost, duration, error.
  6. Review verdict: the review prompt asks for a final VERDICT: line; extract_verdict() maps it to comment or request_changes. Anything else is comment. APPROVE is unreachable by construction.

DryRunAgents replaces the runner under --dry-run: it writes the expected output files and returns success, which is how the full flow is exercised offline in under a minute (test plan T-I7-8).

10Jira, GitHub and workspace clients

JiraClient

httpx with basic auth, retries on 429 and 5xx, dry-run mode that logs writes. Endpoints used: POST /rest/api/3/search/jql (paged with nextPageToken), GET/POST issue/{key}/transitions (by name; raises TransitionUnavailable with the available names), POST issue/{key}/comment (ADF body), POST issue/{key}/remotelink, POST project (team-managed Kanban template), POST statuses and the workflows bulk read, validate and update endpoints to add the status set to a project's workflow (statusReferences must be UUIDs).

GitHubClient

No GitHub SDK: every call is gh or git through an injectable runner (argv, cwd, stdin), which is what the unit tests replace. Rules baked into the client:

  • pr_review refuses APPROVE and prefixes bodies with [ains review agent].
  • pr_merge refuses unless human_approved and ci_green; the engine only relaxes human_approved when G3 is off.
  • _to_pr keys checks by full name and by last segment, because a reusable workflow called from job ci reports as ci / ci; ci_green reads checks["ci"].
  • ci_failure_log takes the latest ci run on the branch and failed_step_excerpt() windows 60 lines before the last ##[error] marker, stripping the job\tstep\ttimestamp prefixes; the whole-job tail is service-container teardown noise.
  • Commits pass -c user.name/-c user.email from AINS_GIT_NAME/EMAIL with the Dockerfile defaults; pushes authenticate through credential.helper "!gh auth git-credential".
  • Write operations are skipped and logged under dry_run.

Workspace

/work/<KEY>/ is a clone of the target on the story branch <KEY>-<slug>. commit(key, stage, message) commits only if git status --porcelain is non-empty. cleanup deletes the directory after merge. The directory survives restarts because it lives on the named volume.

11The GitHub Actions side

  • reusable-ci-python: astral-sh/setup-uv with enable-cache: false, uv sync, uvx ruff check . && uvx ruff format --check . (ruff as a tool so targets need not declare it), uv run pytest, then a nested call to the Jira callback with transition Code Review. The issue key is taken from the branch name.
  • reusable-release: builds only if a Dockerfile exists; without one the environment jobs still run so the gates are exercised. The issue key is parsed from the squash-merge commit subject (AINSSB-2: ...), which is why the orchestrator's PR titles start with the key.
  • reusable-jira-callback: curl against REST v3 with JIRA_EMAIL and JIRA_API_TOKEN from the target repo's secrets.
  • intake-ack: listens to repository_dispatch on the platform repo; an optional audit trace, not a trigger.

12Onboarding internals

Onboarder.add(repo_name, jira_key, jira_name, gates, approval_mode) runs these steps in order, each idempotent and each reported as planned (dry run), done, exists or failed:

  1. github repo: gh repo create private, or reuse.
  2. templates: clone to a temp dir, render bootstrap/templates/ (placeholders {{platform_repo}}, {{platform_ref}}, {{jira_base_url}}, {{image_name}}), run specify init --here --force --non-interactive --integration claude --ignore-agent-tools, commit if dirty, push.
  3. labels: ai-review, g3-approved, g3-rework, ai-native.
  4. secrets: JIRA_EMAIL, JIRA_API_TOKEN via gh secret set.
  5. environments: staging, production with the PAT owner as required reviewer (REST).
  6. branch protection: main requires the context REQUIRED_CHECK_CONTEXT = "ci / ci", no force pushes, admins not enforced (so the engineer can repair main by hand).
  7. jira project: create team-managed Kanban project if the key is free; jira statuses: create missing statuses and add them to the project's workflow via the workflows update API; jira lane: verify the label convention; jira automation: print the manual checklist.
  8. targets.yaml: append the block. Running inside the container this file is read-only, so onboarding is run on the host with uv run ains target add.

remove reverses the platform-owned pieces and leaves the repository unless --delete-repo.

12cPortal, profiles and the management skill

Portal (portal.py, portal_templates/)

FastAPI with Jinja2 templates, started by ains portal and run as the compose service portal on the same image. A Portal object resolves config root, data and work dirs once; every request reloads load_config() and opens the store, so edits to the mounted files show at once. Read routes: / (dashboard), /projects/{KEY}, /stories/{KEY}, /platform, /docs/{name} (served from the mounted docs/), /api/status (the same rows as ains status --json). Write routes start background jobs and redirect to /jobs/{id}: POST /add (Onboarder.add), POST /projects/{KEY}/remove (typed confirmation, dry-run default, Onboarder.remove), POST /projects/{KEY}/verify (verify_target). Jobs are in memory (JOBS), so a portal restart forgets their reports; the store and the Jira comments keep what matters. The story page draws the state map from FSM_NODES and fsm_current(), which combines the live Jira status, the live PR state (pr_view) and the stage, with stage-implied fallbacks when Jira or GitHub are unreachable. The portal only reads Jira and GitHub; gates are never passed from it.

Profiles (profiles.yaml, config.Profile)

The catalog mirrors the delivery view of "AI driven SDLC for IT": project classes (Layer 1, with an autonomy_ceiling), lifecycle phases (Layer 2, all fixed in the story flow today), methodologies (Layer 3) and autonomy levels (Approach 2, with the gate set each implies). Each entry has supported; validate_profile() refuses unknown or unsupported choices, a fixed phase left out, and a level above the class ceiling; gates_for_autonomy() is the gate default for target add and the portal form. The chosen profile is stored on the target (Target.profile) and written into the targets.yaml block. To add an option: add the catalog entry, build what it needs (a flow variant, a prompt set, a workflow), then flip supported; the portal greys it out until then.

The management skill (.claude/skills/ains/, invoked as /ains)

A Claude Code skill for operating the platform from a terminal session in this repository (mirrored in the PoC workspace). It holds no state: every answer comes from ains status --json, ains session status --json, /api/status and gh, which read the same store the portal shows. Requests are free-form; onboarding and removal are guided, one question per turn through the question tool, with the options read from profiles.yaml at the time of asking, a dry run shown before the real run, and verify afterwards. It refuses to pass gates unless the user names the exact action, and it never writes tokens anywhere but .env and repository secrets. Keep reference.md in step with the command sheet in the user guide.

Flow tests drive the engine with run_until(engine, store, key, stage). The GitHub client is tested by recording the gh/git argv through FakeRunner.
  • Test names carry the test-plan id (test_T_I4_7_...) so the traceability matrix in plan/ains-platform-test-plan.md can be checked by grep. Add a row there for every new behaviour.
  • Log every change in docs/implementation-log.md: what was observed, the cause, the fix, the commit. The user has asked for that log to be always current; it is also the acceptance evidence.
  • Plan copies: the working plan lives outside the repo in PoC/plan/; copy both files into plan/ when they change, and check the diff direction first.
  • Windows: the CLI reconfigures stdout with errors="replace"; keep .gitattributes LF normalisation; prefer small Python patch scripts over shell heredocs when the text contains backslashes.
  • Regression: after any flow change, run a story through the sandbox (AINSSB). The dry-run flow test (T-I7-8) is the fast offline equivalent.

14Extending the platform

Add a stage (for example a docs agent after implement)

  1. Add the stage to flows/story.yaml stages and, if it ends in a gate, to gates; add any new Jira status names under jira_status and to the onboarding status list.
  2. Add a prompt template under agents/stages/ and a stage block in agents/claude-code.yaml.
  3. In flow.py: declare its outputs in STAGE_OUTPUTS (resume skips the agent when they exist), write a handler, and register it in step()'s dispatch. Reuse _run_stage_and_gate if the stage is "run agent, commit, set a review status, wait".
  4. Add rows to the state table in the plan (9.3) and parametrised cases to test_flow.py.

Change how a gate is approved

Jira gates: _wait_jira_gate compares the status to the flow's approve name; change the name in story.yaml. G3: _do_wait_g3 reads PullRequest.human_approved, which _to_pr derives from reviews (review mode, ignoring the bot and the agent marker) or labels (label mode). A new signal, for example a required reviewer team, belongs in _to_pr, not in the engine.

Add a flow

Drop a second YAML into flows/ and reference it from a target's flow. FlowEngine reads stage order and gates from the flow, but the handlers are the ones in flow.py; a flow with a stage the engine does not know fails validation at load.

A second harness

Not planned: subscription tokens are only valid inside Claude Code, and the orchestrator deliberately has no model API client. If a harness is ever added, it is a new AgentRunner implementation selected by agents/*.yaml, and it must keep the prompt-on-stdin and minimal-env contract.

Another language stack for targets

Add reusable-ci-<stack>.yml next to the Python one and a matching bootstrap/templates/ci.yml variant selected by a new target add --stack option; keep the job name ci so the check context stays ci / ci.

15Invariants and security model

Breaking any of these needs a plan decision, a test change and a log entry, in that order.
  • The orchestrator never merges without human_approved and ci_green (client guard), except that an off G3 counts as approval.
  • The review agent never approves: pr_review rejects APPROVE; the verdict parser cannot produce it.
  • No agent process ever sees ANTHROPIC_*; the config schema, minimal_env and ains doctor all check it.
  • Agents cannot push, commit, merge, fetch the web or read .env (deny list in both settings files; the review stage additionally has no edit tools).
  • Secrets live in .env (gitignored) and in target repo secrets; nothing in docs/, plan/ or the log ever holds a token value. Rotate all three after the PoC.
  • The container has no inbound network; every integration is a poll or a subprocess.
  • One transition per session per cycle; every transition writes an event before it returns.
  • A project cannot change platform content except through Jira, GitHub and the portal API. Inside a project repository the platform-owned paths (.github/, .claude/, .specify/, CLAUDE.md) are protected three ways: deny rules in both agent permission files (Edit/Write/MultiEdit on those paths), the CI platform guard step in reusable-ci-python.yml (settings file must equal the template, thin workflows must call the platform, CODEOWNERS must exist), and CODEOWNERS with code-owner reviews required when the target's approval mode is review. target verify reports drift of the settings file. GitHub environment reviewers follow the gates: staging has one only when G4 is on, production only when G5 is on.

17Known limits and backlog

  • G3 in review mode needs a second GitHub account (bot_login); untested live.
  • Onboarding must run on the host because targets.yaml is a read-only mount in the container.
  • The Jira Automation rule is manual and optional; Jira statuses are created by API but the board columns are not arranged.
  • Cost per agent run is recorded from the CLI's total_cost_usd for information only; the subscription is what is billed.
  • The release workflow runs on every push to main, including hand edits; a run without an issue key moves nothing in Jira but still asks for approvals.
  • Plan steps still open after the AINSSB-2 acceptance: human-lane PR review (8.12), second onboarding and removal proof (6a.2), divergence notes and milestone close (9).
