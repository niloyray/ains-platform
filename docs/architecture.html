01Overall approach

This PoC does not invent a new architecture. It takes the organization's already-defined delivery view — class, loop, method, agent harness, tools, model gateway, wrapped by governance — and fills every layer with one concrete, minimal product so the pattern can be exercised end to end on real infrastructure, not just described. The platform is built first as its own repository, ains-platform, and then used to build a separate PoC repository, ains-poc, so the platform can evolve and host further PoCs. Jira, the orchestrator and GitHub Actions belong to the platform but are used only by PoC stories; ains-platform is edited directly in VS Code with the Claude Code CLI, with no story lane or CI of its own.

One story's journey: a Jira story in project AINSPOC with Execution Lane = AI-native enters at Layer 1. ains-orchestrator, a homegrown container on the laptop, polls Jira, claims the story and runs the organizational loop (Layer 2), loading Spec Kit as the active method (Layer 3) to turn the story into spec.md / plan.md / tasks.md. It dispatches the Claude Code CLI headless as the stage agent (Layer 4) to implement against tasks.md in a clone of ains-poc. The work moves through the tools that carry the phases (Layer 5) — the target GitHub repo, reusable GitHub Actions workflows owned by ains-platform, Docker Compose and Postgres for the running application — authenticated against a single Claude Max subscription at Layer 6, since this PoC has no model gateway. Five human gates (spec, plan, code, staging, production) can each be switched on or off per target. The loop closes when the reusable release workflow calls Jira's API to move the story to Done and link the PR.

Governance in this PoC is deliberately thin — enough to trace one run end to end, not enough to operate at organizational scale. Section 05 lists exactly what's missing against the full pattern; that gap list is itself a finding of the research, not an oversight to hide.

02Layer-by-layer

  • Layer 1 — class and intake. One Jira project, AINSPOC, holding PoC stories only, with an Execution Lane field (Human · AI-native). The platform has no Jira project. No class router: every AI-native story takes the same path, and the lane field is the only routing decision.Why it matters at org scale: the router is what lets light work move fast and critical work stay controlled, without either negotiating exceptions.
  • Layer 2 — one organizational loop. intake → spec → plan → develop → test → deploy → maintain, run headless by ains-orchestrator, a homegrown Python service in a Docker container that polls Jira rather than receiving a webhook.It stands in for the org pattern's A4c orchestration-service role — the headless runner for work with no person at the surface. No public "Ark" matched the original description, and API-agnostic orchestrators would need metered API keys.
  • Layer 3 — method as a loaded skill. Spec Kit is the method; its templates are laid down by the platform's bootstrap script and its output is committed into the target repo under specs/<JIRA-ID>/ rather than drawn from a central, versioned catalog.The org pattern packages methods as signed, versioned skills from a registry (AG1) so they can be updated centrally — this PoC's "catalog" is a template folder in ains-platform.
  • Layer 4 — agent harness and orchestration. Claude Code CLI is the one agent harness, spawned by ains-orchestrator as a fresh headless process per stage (spec, plan, implement, review) with ains-poc as its only target; humans use VS Code with the Claude Code CLI for Phase 1 platform work and for Human-lane stories in Phase 2. Five switchable gates G1–G5 are the human control points.The org pattern defines eight stage agents, one per phase, each taking its role from the loaded method. This PoC implements one, and the agent layer is a command template so other CLIs can be added later.
  • Layer 5 — tools carrying the phases. Jira (work management) · GitHub repos ains-platform and ains-poc (code and specs) · reusable GitHub Actions workflows (CI, release, Jira callback, intake-ack) defined in ains-platform and executed only in ains-poc · Docker Compose and Postgres (the running application's environment).The knowledge graph and partner/external agents (A5e, A5g in the org pattern) aren't part of this stack — there's no enterprise context layer to query yet.
  • Layer 6 — model access. Direct to a Claude Max subscription via CLAUDE_CODE_OAUTH_TOKEN, consumed only by the Claude Code CLI; the orchestrator never calls a model API. No gateway, no metering.Anthropic restricts subscription tokens to Claude Code itself, which is exactly why the orchestrator dispatches the CLI rather than calling models. The org pattern's model gateway exists to standardize this across many teams; a single-person PoC doesn't need it yet.

06Implementation steps

  1. Platform repo. Create github.com/niloyray/ains-platform; it holds the orchestrator, flows, agents, reusable workflow definitions, bootstrap script and docs. It is edited directly and runs no Actions of its own.
  2. Jira. Create project AINSPOC for PoC stories only; add the Execution Lane field, the nine statuses (Ready → Specifying → Spec Review → Plan Review → Implementing → Code Review → Staging → Done, plus Rework, Blocked) and one Automation rule that sends a repository_dispatch as an audit trace.
  3. Orchestrator container. Build the ains-orchestrator image (Python, Claude Code CLI, Spec Kit, git, gh) and run it with Docker Compose on the laptop; confirm ains agent list, ains flow list, ains targets list and specify check.
  4. Flow definition. spec → G1 → plan → G2 → implement → review → G3 → merge, one spawned Claude Code CLI process per stage, the review agent posting a PR review before the human G3 approval, gates switchable per target in targets.yaml.
  5. Claude Code auth. Run claude setup-token locally; store CLAUDE_CODE_OAUTH_TOKEN in the gitignored .env the container reads. The orchestrator passes it only to claude -p subprocesses.
  6. Reusable workflows. CI (ruff · pytest + Postgres · docker build), release (GHCR → staging G4 → production G5), Jira callback and intake-ack, all workflow_call in ains-platform.
  7. Bootstrap the PoC repo. bootstrap/new-target.sh creates ains-poc, its secrets and environments, thin caller workflows, Spec Kit templates and the targets.yaml entry; the GitHub PAT also goes into the Jira Automation rules.
  8. End-to-end acceptance run. Run AINSPOC-1 through all five gates before building the PoC app — the platform validating itself, and the only Phase 1 use of Jira, the orchestrator and Actions.
  9. Phase 2. Build the FastAPI + Postgres app story by story through the AI-native lane, with Human-lane stories in VS Code + Claude Code CLI alongside — covered in the companion build prompt.
  10. Record the gaps. Section 05's gap list and docs/divergence.md are research deliverables, not a punch list to silently fix.
ains-orchestrator runs outside GitHub Actions The orchestrator needs a machine that stays on; it's the Layer 2/4 runner, not something GitHub's ephemeral runners can host. For this PoC that machine is a Docker container on the laptop, so polling pauses when the laptop sleeps — recorded as a divergence. Actions still owns Layer 5's CI and release — it never dispatches the agent.

07Open questions

Homegrown orchestrator

No public project matched the "Ark" CLI this document originally described; API-agnostic orchestrators (McKinsey ARK, OpenHands) need metered API keys, and harness-agnostic ones (yokai, chipping-orchestrator) lack Jira-to-GitHub. ains-orchestrator is therefore self-built and is itself a research subject — keep it small and tested.

OAuth token ownership and scope

Tied to whoever ran claude setup-token and valid only inside the Claude Code CLI — Anthropic blocks subscription tokens in third-party harnesses. Fine for this solo PoC; a shared team setup would switch to an API key, which is closer to Layer 6's gateway pattern anyway.

Phase order and tooling

The platform is built first (Phase 1) in VS Code with the Claude Code CLI, then ains-poc is developed on it (Phase 2) with the same tooling for the Human lane. Jira, the orchestrator and Actions are deliberately kept out of the platform's own change flow; whether the platform should later dogfood its own lane is left to the Phase 2 findings.

Spec Kit vs. OpenSpec

The org framework's A3a lists Spec Kit by name alongside BMAD, OpenSpec and GSD as method options — this PoC uses GitHub's Spec Kit specifically, integration key claude.
