AINS · AI-native software delivery platform

Taking a project from a written idea to a released change, step by step

This guide is for people who will use the platform without knowing Jira, Git, GitHub or GitHub Actions. It names every piece you will see on screen, says who does what, and walks one project through setup, onboarding and the delivery of a single story.

1The idea in one picture

A person writes what they want as a short story in Jira. The platform picks it up, and four AI agents do the work in turn: one writes the specification, one writes the plan, one writes the code and tests, one reviews the code. Between those steps the platform stops and waits for a person to look and say yes, or send it back. After the last yes the change is built and released. Nothing is merged or released without a human decision at the gates that are switched on.

2The words you will meet

You do not need to learn the tools. You need to recognise these names when they appear on screen.

Jira
The board where work is written down. Each item is a story: a short text saying what should change and how you will know it is done. A story is always in exactly one status (for example Ready or Spec Review). You change a status by dragging the card to another column or by picking a status from the drop-down on the story. A comment is a note under the story; the platform writes one at every step so the story is its own diary. A label is a tag on the story; the label ai-native tells the platform "this story is yours".
GitHub
The website where the project's files live. A repository ("repo") is one project's folder with its full history. The main branch is the official version of that folder.
Branch
A private working copy inside the repository, named after the story (for example AINSSB-2-repository-scaffold). Agents work there so the official version is untouched until a person agrees.
Commit
One saved set of changes with a one-line message. The platform prefixes every message with the story key, like AINSSB-2: implement tasks.md.
Pull request (PR)
A web page on GitHub that proposes merging a branch into main. It shows the changed files side by side, the test results, reviews, and labels. It is where you make the code decision. A PR starts as a draft (not ready) and is later marked ready for review.
Merge
Accepting a PR. Its changes join main and the PR shows a purple "Merged" badge. The platform merges for you, only after the gate is passed.
GitHub Actions
GitHub's automation. A workflow is a script that runs when something happens. A run is one execution; you see runs under the repository's Actions tab.
CI, the check
The workflow that installs the project, lints it and runs its tests every time the PR changes. On the PR it appears as a check named ci / ci with a green tick (passed) or a red cross (failed).
Environment
A named release stage inside GitHub, here staging and production. Each one is set to require a named person to approve before the workflow continues. That approval is a gate.
Image, GHCR
The packaged, runnable form of the project, stored in GitHub's container registry. The release workflow builds it once and tags it staging and then production.
Docker
The program that runs packaged software in isolated boxes called containers. The orchestrator runs in one on the platform engineer's laptop.
Orchestrator
The platform's own program, called ains. It watches Jira, starts agents, opens and updates the PR, waits at gates and keeps a record of every step.
Agent
One run of the Claude Code command-line program with a task written by the orchestrator. It can read and edit the files in the branch and run the tests. It cannot push, merge, approve or reach the internet. When the task is done the program ends; nothing lingers.
Spec Kit
A set of ready-made instructions the agents use so that specifications, plans and task lists always have the same shape and land in the same folder, specs/<story key>/.
Gate
A point where the platform stops and waits for a person. There are five. Each can be switched on or off per project.

4One-time platform setup

Done once by the platform engineer, on the laptop that will run the orchestrator. Everything in this section stays on that laptop; none of it is needed by the people who write stories or approve gates.

What you need before you start

  • Docker Desktop installed and running.
  • A GitHub account that owns the project repositories, plus a classic personal access token with the repo and workflow scopes. GitHub: Settings → Developer settings → Personal access tokens.
  • A Jira Cloud site and an API token for your Atlassian account (id.atlassian.com → Security → API tokens).
  • A Claude subscription (Max). Run claude setup-token once in a normal terminal on the laptop; it opens the browser, you approve, and it prints a token starting with sk-ant-oat01-. That token makes the agents use your subscription, never a pay-per-use API.
Tokens are passwords. They go into one file, ains-orchestrator/.env, which Git is told to ignore. Never paste them into a story, a PR, a document or a chat.
step1

Get the platform

platform engineerterminal
git clone https://github.com/niloyray/ains-platform
cd ains-platform/ains-orchestrator
copy .env.example .env

Open .env in an editor and fill in CLAUDE_CODE_OAUTH_TOKEN, GITHUB_TOKEN and GH_TOKEN (same value), JIRA_BASE_URL, JIRA_EMAIL, JIRA_API_TOKEN. Leave every ANTHROPIC_* line absent.

step2

Build and start the orchestrator

platform engineerterminal, in ains-orchestrator
docker compose up -d --build

This builds a container image with the orchestrator, the GitHub command-line tool, Claude Code and Spec Kit, then starts it. It polls Jira every 60 seconds from now on. Repeat the same command after any change to the platform code; configuration files (targets.yaml, the flow, the agent prompts, the agent permission file) are mounted and picked up without a rebuild.

You should see: Container ains-orchestrator Started, and docker compose ps reports it as healthy.

step3

Check the connections

platform engineerterminal
docker compose exec orchestrator ains doctor

Checks that Jira answers with your account, that GitHub accepts the token, that Claude Code starts with the subscription token, and that no API key is set. Fix anything that is red before going on.

5Onboarding a new project

One command creates everything a project needs on GitHub and in Jira and registers it with the orchestrator. Pick three names first: the repository name (lower case, hyphens), the Jira project key (2 to 10 capital letters, this prefixes every story, for example AINSPOC), and the Jira project's display name.

step1

Run the onboarding command

platform engineerterminal, in ains-orchestrator
ains target add

With no arguments the command is a guided wizard: it asks for each value in turn, with numbered choices where there are options (repository name, Jira key and name, project class, autonomy level, methodology, G3 approval mode, gates), shows the full command your answers amount to, runs it as a dry run, and asks before running it for real. Afterwards it verifies the project and reminds you to commit the target entry. ains works from any folder once ains.bat is in a folder on your PATH (the platform engineer's copy is in %USERPROFILE%\.local\bin); a bare ains prints the quick start.

The one-line form does the same without questions, and is what the wizard prints at the end:

ains target add ains-poc AINSPOC "AINS PoC" --class small-poc --autonomy L3 --methodology spec-kit --approval-mode label --dry-run

Drop --dry-run to run it. The command is safe to run again: it reports what already exists and re-applies the rest. The same form exists in the portal under + Add project.

The profile. Every project states what kind of work it is, in the words of the delivery framework: a project class (small projects and proofs of concept, enterprise greenfield, feature work on AI-native applications; legacy and modernization classes are listed but not supported yet), the lifecycle phases it runs (intent, specification, plan, develop, test, deploy; maintain is not supported yet), the methodology (Spec Kit; others listed, not yet) and the autonomy level. The autonomy level sets the gates: L3 Agentic keeps all five human gates; L4 Harness-driven keeps only G3 code and G5 production and auto-passes the rest. Each class has a ceiling (greenfield stops at L3). Unsupported choices are refused with the reason; the catalog is ains-orchestrator/profiles.yaml, so new options are added there as the platform grows.

6Delivering one story

This is the daily path. It is shown with all five gates on. Times are what the sandbox run showed: each agent run takes between fifteen seconds and two minutes, and the orchestrator looks for work once a minute, so a stage normally completes within three minutes of your decision.

step1

Write the story

product ownerJira, the project board
  • Click Create, type Story. Give it a one-line summary (this becomes the PR title and the branch name) and a description that says what should change and how to tell it is done. Two to eight sentences is the sweet spot; the spec agent asks no questions, so what is not written is guessed.
  • Add the label ai-native. Without it the platform ignores the story.
  • Leave it in To Do until you want work to start, then move it to Ready.

You should see within about a minute: the status changes to Specifying by itself and a comment from the platform appears under the story.

step2

The specification is written

orchestrator + spec agentautomatic

The orchestrator makes a copy of the repository, creates the story's branch, and starts the spec agent with your story text. The agent writes specs/<KEY>/spec.md. The orchestrator commits it, opens a draft pull request titled with the story key and summary, links the PR under the story, sets the status to Spec Review and comments with what to do next.

gateG1

G1, approve the specification

product ownerJira, with the PR open in another tab
  • Open the PR link from the story's comment. Click the Files changed tab and read specs/<KEY>/spec.md. Ask: is this what I meant?
  • Yes: in Jira, move the story to Planning.
  • No: write a comment on the story saying what is wrong or missing, then move it to Rework. The newest comment is handed to the spec agent and it rewrites the spec. The story comes back to Spec Review.
step3

The plan is written

orchestrator + plan agentautomatic

The plan agent reads the spec and writes plan.md (how it will be built) and tasks.md (a checklist of concrete tasks) next to it. Both are committed to the same PR. Status becomes Plan Review.

gateG2

G2, approve the plan

product ownerJira, with the PR open
  • Read plan.md and tasks.md under Files changed. Check the scope: nothing missing, nothing extra.
  • Yes: move the story to Implementing.
  • No: comment, then move to Rework. The plan agent runs again with your comment.
step4

The code is written, tested and reviewed

implement agent, CI, review agentautomatic
  • The implement agent works through tasks.md, ticking each task, writing code and tests, and running the tests until they pass. It cannot commit or push; the orchestrator commits what it left and pushes.
  • The PR is marked ready for review. That starts the CI workflow, which installs the project, lints it and runs the tests. The result shows on the PR's Checks tab as ci / ci. CI also moves the story to Code Review.
  • The review agent reads the diff and the CI result with read-only permissions and posts a review on the PR, starting with [ains review agent]. It can comment or ask for changes; it can never approve or merge.

You should see on the PR: new commits, a green or red check, and a review from the orchestrator account. In Jira: Code Review.

gateG3

G3, approve the code

reviewerGitHub, the pull request
  • Checks tab: ci / ci must show a green tick. A red cross next to an older commit in the Conversation tab is history; what counts is the newest commit.
  • Conversation tab: read the agent's review. Files changed tab: read the code if you want to.
  • Yes: in the right sidebar click the gear next to Labels and tick g3-approved.
  • No: write what should change as a comment at the bottom of the Conversation tab, then add the label g3-rework. The implement agent runs again with your comment, pushes, CI runs, the review agent reviews, and the PR waits for you again.
  • CI is red: do nothing. The orchestrator sends the failed test output back to the implement agent by itself, up to two rounds. After that the story goes to Blocked with a comment, and a person has to look.

Why a label and not the Approve button: GitHub does not let an account approve a PR it opened itself. On a single-account setup the label carries the same meaning. With a separate orchestrator account the project can use --approval-mode review and the normal Approve button instead.

The two approval modes, and the second account. In label mode one GitHub account does everything: the orchestrator opens and merges PRs under your token, and you approve with the g3-approved label. In review mode the orchestrator has its own GitHub account, a plain second user with write access to the project repositories; its token sits in .env as AINS_BOT_GITHUB_TOKEN next to AINS_BOT_LOGIN. The orchestrator then opens, pushes and merges as that account, and you approve with GitHub's real review, Approve or Request changes, because the PR is no longer yours. Branch protection then also requires a code-owner review for the platform-owned files. Onboarding invites the bot account to every project and accepts the invitation with the bot's token, so nobody clicks an e-mail. A reviewer never needs a token: reviewing happens in the browser with the reviewer's own login. The platform engineer's own token stays in .env too, used for onboarding and verification, since creating repositories needs the owner. Switching a project from label to review takes effect for pull requests opened after the switch; a PR opened under your own account can only be approved by the label.

step5

Merge and build

orchestrator, release workflowautomatic

On its next poll the orchestrator sees the label and the green check, squash-merges the PR (all the story's commits become one on main), comments in Jira with the PR link, and deletes its working copy. The merge starts the release workflow, which builds the container image, pushes it to the registry, and then stops to wait for G4.

You should see: the PR badge turns purple, "Merged". Under the repository's Actions tab a run named release with a yellow status.

gateG4

G4, approve staging

release approverGitHub, Actions tab
  • Open the release run. A yellow banner says a deployment is waiting for review. Click Review deployments, tick staging, optionally leave a comment, click Approve and deploy.
  • The image is tagged staging. The workflow moves the story to Staging in Jira and comments with the run link.
  • To stop the release: click Reject instead. The run ends and the story stays where it is.
gateG5

G5, approve production

release approverGitHub, the same run

The same run pauses again. Review deployments, tick production, Approve and deploy. The image is tagged production and the story moves to Done.

The story's comments now hold the whole trail: every claim, every agent run, every gate decision, the PR link and the release run link.

A story that does not need all this: switch gates off for the project (section 7). An off gate is passed automatically and the platform leaves a comment saying so, so the trail never has a silent skip.

What a project may and may not change

A project influences the platform only through the doors it was given: Jira statuses and labels, GitHub labels and pull requests, and the portal. The platform's own state and configuration are out of reach. Inside the project's repository four things belong to the platform and must not be edited there: the .github folder (workflows and CODEOWNERS), the .claude folder (the agents' permissions and skills), the .specify folder and CLAUDE.md. Three guards enforce that:

  • Agents cannot edit them. The permission file every agent runs with denies edits to those paths, whatever a story asks.
  • CI blocks drift. Every pull request runs a platform guard that fails if .claude/settings.json differs from the platform template, if the thin workflows no longer call the platform's reusable workflows, or if CODEOWNERS is missing. A red check cannot be merged.
  • Code owners. CODEOWNERS names the platform engineer for those paths. In review approval mode GitHub requires that review before a merge; on a single account the CI guard does the blocking.

To change one of those files, change the platform (the template) and re-run ains target add for the project; it refreshes them in place.

Working locally alongside the platform

The sandbox and every onboarded project live on GitHub and in Jira; nothing of them is on your laptop until you clone them. Clone anywhere, for example next to the platform folder:

gh repo clone niloyray/ains-sandbox
cd ains-sandbox

Two ways to work from that clone, both compatible with the flow:

  • Your own change, no agents (the human lane). Branch, commit, push, open a pull request as usual. CI runs and the platform guard runs; branch protection requires the green check. Add the label ai-review if you want the review agent's opinion; it reviews once per commit and never merges. Merge it yourself. The release workflow then builds and waits at the environments exactly as for an agent story. Name the branch and commits after a Jira story (AINSSB-7-..., AINSSB-7: ...) if you want the release callbacks to move that story; without a key they move nothing.
  • Joining an agent's story. The story's branch is on GitHub (<KEY>-<slug>, linked from the Jira comment and the PR). Check it out, commit, push. Do this while the story is waiting at a gate, which ains status shows as wait_g1, wait_g2 or wait_g3: at G1 or G2 you can edit the spec or the plan before approving; at G3 a pushed commit makes the review agent review again and CI run again. Every agent stage starts from the branch's remote tip, so your commits are kept and built upon. Do not push while a stage is running (spec, plan, implement, review): the orchestrator would push on top of a branch that moved and the stage would fail and retry. The cleaner way to steer an agent is still a Rework comment or g3-rework; use direct commits for small fixes.

Things that stay with the platform even when you work locally: the four platform-owned paths (section 6, a pull request touching them fails the guard), merging an agent's PR (the orchestrator does it after G3), and the Jira statuses the platform sets.

A pull request a person wrote

Developers can keep working the ordinary way. Add the label ai-review to any PR in an onboarded repository and the review agent reviews it once per new commit. Merging it is still a human decision; nothing else changes.

8The four agents

Each agent is a fresh, headless run of Claude Code inside the orchestrator's container, with a prompt the orchestrator renders from a template, a turn limit, a wall-clock limit of 30 minutes, and a permission file that lists what it may run. It receives only the subscription token; no API key can reach it. If a run fails, the orchestrator retries once after five minutes, then marks the story Blocked.

The prompts live in ains-orchestrator/agents/stages/ and the limits in agents/claude-code.yaml. Rework hands the agent the human's comment under a heading "Rework requested by the reviewer"; a CI failure hands the implement agent the failing step's output.

The management portal

Open http://localhost:8787 on the laptop that runs the platform, or type ains-platform.cmd portal. It reads the same database as the orchestrator, so it never disagrees with the commands below. The left bar has:

  • Dashboard: is the poller alive (last cycle and age), are the credentials present, which stories wait for a person and what to do, every story, recent events and jobs.
  • Platform: the running flow, agents, gates, config files and where the data lives.
  • Projects: one page per project with its gate cards, profile, Jira and GitHub links (board, pull requests, actions, environments, protection, labels, secrets, images), every story with its next action and links to spec, plan, tasks, diff, checks and CI runs, a Run verify button and a Remove form with typed confirmation and dry run.
  • + Add project: the onboarding form: names, project class, lifecycle phases, methodology and autonomy level, with the gates filled from the level. Options the platform cannot run yet are greyed out with "not yet". Dry run first.
  • Story page (click a story): stage, live Jira status and pull-request state, the next action, the state map with the current states highlighted, artifact links and the full event trail including what each agent replied.
  • Documentation: this guide, the developer manual and the implementation log, served from the repository.

Onboarding, removal and verify run as background jobs; the job page refreshes until the report is complete. The portal is only reachable from the laptop itself.

Asking Claude Code instead: the /ains skill

If you work in a Claude Code terminal opened in the platform repository (or in the PoC folder above it), a skill called ains is loaded. It is not a command with fixed subcommands: you write a request in plain words and Claude turns it into the right platform command, reads the result and answers in your words. Type the slash form to make it explicit, or just ask; both use the same instructions.

/ains status
/ains what is waiting for me
/ains why is AINSSB-3 blocked
/ains what did the implement agent say on AINSSB-3
/ains verify the sandbox
/ains add a project
/ains start the platform and show the log

Adding a project this way is guided. Say /ains add a project and Claude asks one question at a time, each with options to pick from: repository name, Jira key and name, project class, autonomy level (only the levels the class allows, each showing the gates it switches on), G3 approval mode, and whether to keep those gates. Phases and methodology are not asked while only one option is supported. It then shows the exact command, runs it as a dry run, shows the planned steps, and asks before running it for real; afterwards it verifies the project and reminds you to commit the target entry. Anything you already said in the request is not asked again.

The skill keeps no record of its own. Every answer is read from the platform's store in the container, the same database the portal shows, so the terminal and the portal never disagree. It will not pass a gate, merge, approve as the agent, or put a token anywhere but the .env file and repository secrets. It approves a gate only when you name the exact action, for example "add g3-approved to PR 5", and then does only that.

The one-line answer: what is waiting for me?

docker compose exec orchestrator ains status

Lists every story the platform knows with its stage and, under it, the one thing a person can do now, for example:

AINSSB-2     released   pr=#2  updated 2026-11-03T02:07:40+00:00
    next: G4/G5: in GitHub Actions open the release run for PR #2, Review deployments, approve staging then production...
AINSSB-3     wait_g1    pr=#3  updated 2026-11-03T02:40:12+00:00
    next: G1: in Jira move AINSSB-3 to Planning (approve) or to Rework with a comment (send back)

Run it whenever you come back to the platform. Add --json for a machine-readable version.

Is a project onboarded correctly?

uv run ains target verify ains-sandbox AINSSB

Reads, and never changes, everything onboarding should have created: the repository and its starter files, the four labels, the two secrets, the two environments with a required reviewer, the branch protection on main, the Jira project and its twelve statuses, and the entry in targets.yaml. Each line is [ok] or [FAIL] with the reason. Run ains target add again to repair anything that fails; it only creates what is missing.

Docker Desktop (no terminal)

Open Docker Desktop, click Containers, then ains-orchestrator. The Logs tab shows the same text as the commands below, with a search box. A green dot and "Running" next to the name means the platform is alive.

The container log

docker compose logs -t --since 30m orchestrator     # last 30 minutes, with timestamps
docker compose logs -t -f orchestrator              # follow live; Ctrl+C stops watching, not the platform
docker compose logs --since 2h orchestrator | Select-String -NotMatch "wait_g3'}"   # PowerShell: hide idle repeats

Once a minute the orchestrator prints one line, for example:

2026-11-03T02:07:40Z cycle: claimed=[] stepped={'AINSSB-2': 'released'} skipped=[] reviewed=[] errors=[]
  • claimed: stories it picked up from Ready in this cycle.
  • stepped: each active story and the stage it is in after this cycle. A stage starting with wait_ means it is waiting for a person; the same line repeating every minute is normal.
  • reviewed: pull requests labelled ai-review that got an agent review.
  • errors: anything that failed this cycle, with the story key.

Between cycle lines you may see lines such as agent implement for AINSSB-2: claude (max_turns=80, limit=1800s), which mark the start of an agent run. The -t flag adds Docker's own timestamp in front; the cycle line also carries its own UTC time.

One story's event list

docker compose exec orchestrator ains session status AINSSB-2

Prints the story's current stage, branch, PR number and every event with a timestamp: claims, agent start and finish (with turns, seconds and the agent's final reply), gate decisions, rework, merge, blocks. This is the platform's own record and the first place to look when a story did something unexpected.

All platform stories in Jira

In Jira, open Filters → View all issues, switch to JQL and paste:

labels = ai-native AND status not in (Done) ORDER BY updated DESC

Replace status not in (Done) with status = Blocked to see only what needs a person. Save the filter to reach it from the sidebar.

GitHub, by hand

  • Pull requests tab of the repository: every story's PR, open or merged. Filter by the story key.
  • Actions tab: every CI and release run. A yellow dot is "waiting for you"; click the run, then Review deployments.
  • Insights → Network or the branch list: the story branches that exist.

The working copy inside the container

While a story is between spec and merge, its branch is checked out at /work/<KEY> inside the container. To look without changing anything:

docker compose exec orchestrator sh -c "cd /work/AINSSB-2 && git status && git log --oneline -5"

Do not edit files there; the next agent run or commit would pick the edit up as the agent's work. After the merge the directory is deleted.

Where the data lives, and backing it up

Two Docker volumes on the laptop. ains-data holds what must survive: the story database (sessions.sqlite), the poller heartbeat and the log files under logs/. ains-workspaces holds the throwaway clones of story branches. Stopping, restarting or rebuilding the containers keeps both; only deleting the volumes loses them. To take a copy:

ains-platform.cmd backup        # copies the data volume to ains-platform\backup\data-<date-time>

The log file logs/orchestrator.log in that copy is the same text as the container log, kept across container restarts and rotated at 5 MB.
