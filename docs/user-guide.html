AINS · AI-native software delivery platform

Taking a project from a written idea to a released change, step by step

This guide is for people who will use the platform without knowing Jira, Git, GitHub or GitHub Actions. It names every piece you will see on screen, says who does what, and walks one project through setup, onboarding and the delivery of a single story.

1The idea in one picture

A person writes what they want as a short story in Jira. The platform picks it up, and four AI agents do the work in turn: one writes the specification, one writes the plan, one writes the code and tests, one reviews the code. Between those steps the platform stops and waits for a person to look and say yes, or send it back. After the last yes the change is built and released. Nothing is merged or released without a human decision at the gates that are switched on.

2The words you will meet

You do not need to learn the tools. You need to recognise these names when they appear on screen.

Jira
The board where work is written down. Each item is a story: a short text saying what should change and how you will know it is done. A story is always in exactly one status (for example Ready or Spec Review). You change a status by dragging the card to another column or by picking a status from the drop-down on the story. A comment is a note under the story; the platform writes one at every step so the story is its own diary. A label is a tag on the story; the label ai-native tells the platform "this story is yours".
GitHub
The website where the project's files live. A repository ("repo") is one project's folder with its full history. The main branch is the official version of that folder.
Branch
A private working copy inside the repository, named after the story (for example AINSSB-2-repository-scaffold). Agents work there so the official version is untouched until a person agrees.
Commit
One saved set of changes with a one-line message. The platform prefixes every message with the story key, like AINSSB-2: implement tasks.md.
Pull request (PR)
A web page on GitHub that proposes merging a branch into main. It shows the changed files side by side, the test results, reviews, and labels. It is where you make the code decision. A PR starts as a draft (not ready) and is later marked ready for review.
Merge
Accepting a PR. Its changes join main and the PR shows a purple "Merged" badge. The platform merges for you, only after the gate is passed.
GitHub Actions
GitHub's automation. A workflow is a script that runs when something happens. A run is one execution; you see runs under the repository's Actions tab.
CI, the check
The workflow that installs the project, lints it and runs its tests every time the PR changes. On the PR it appears as a check named ci / ci with a green tick (passed) or a red cross (failed).
Environment
A named release stage inside GitHub, here staging and production. Each one is set to require a named person to approve before the workflow continues. That approval is a gate.
Image, GHCR
The packaged, runnable form of the project, stored in GitHub's container registry. The release workflow builds it once and tags it staging and then production.
Docker
The program that runs packaged software in isolated boxes called containers. The orchestrator runs in one on the platform engineer's laptop.
Orchestrator
The platform's own program, called ains. It watches Jira, starts agents, opens and updates the PR, waits at gates and keeps a record of every step.
Agent
One run of the Claude Code command-line program with a task written by the orchestrator. It can read and edit the files in the branch and run the tests. It cannot push, merge, approve or reach the internet. When the task is done the program ends; nothing lingers.
Spec Kit
A set of ready-made instructions the agents use so that specifications, plans and task lists always have the same shape and land in the same folder, specs/<story key>/.
Gate
A point where the platform stops and waits for a person. There are five. Each can be switched on or off per project.

4One-time platform setup

Done once by the platform engineer, on the laptop that will run the orchestrator. Everything in this section stays on that laptop; none of it is needed by the people who write stories or approve gates.

What you need before you start

  • Docker Desktop installed and running.
  • A GitHub account that owns the project repositories, plus a classic personal access token with the repo and workflow scopes. GitHub: Settings → Developer settings → Personal access tokens.
  • A Jira Cloud site and an API token for your Atlassian account (id.atlassian.com → Security → API tokens).
  • A Claude subscription (Max). Run claude setup-token once in a normal terminal on the laptop; it opens the browser, you approve, and it prints a token starting with sk-ant-oat01-. That token makes the agents use your subscription, never a pay-per-use API.
Tokens are passwords. They go into one file, ains-orchestrator/.env, which Git is told to ignore. Never paste them into a story, a PR, a document or a chat.
step1

Get the platform

platform engineerterminal
git clone https://github.com/niloyray/ains-platform
cd ains-platform/ains-orchestrator
copy .env.example .env

Open .env in an editor and fill in CLAUDE_CODE_OAUTH_TOKEN, GITHUB_TOKEN and GH_TOKEN (same value), JIRA_BASE_URL, JIRA_EMAIL, JIRA_API_TOKEN. Leave every ANTHROPIC_* line absent.

step2

Build and start the orchestrator

platform engineerterminal, in ains-orchestrator
docker compose up -d --build

This builds a container image with the orchestrator, the GitHub command-line tool, Claude Code and Spec Kit, then starts it. It polls Jira every 60 seconds from now on. Repeat the same command after any change to the platform code; configuration files (targets.yaml, the flow, the agent prompts, the agent permission file) are mounted and picked up without a rebuild.

You should see: Container ains-orchestrator Started, and docker compose ps reports it as healthy.

step3

Check the connections

platform engineerterminal
docker compose exec orchestrator ains doctor

Checks that Jira answers with your account, that GitHub accepts the token, that Claude Code starts with the subscription token, and that no API key is set. Fix anything that is red before going on.

5Onboarding a new project

One command creates everything a project needs on GitHub and in Jira and registers it with the orchestrator. Pick three names first: the repository name (lower case, hyphens), the Jira project key (2 to 10 capital letters, this prefixes every story, for example AINSPOC), and the Jira project's display name.

step1

Run the onboarding command

platform engineerterminal, in ains-orchestrator
uv run ains target add ains-poc AINSPOC "AINS PoC" --gates G1=on,G2=on,G3=on,G4=on,G5=on --approval-mode label

Add --dry-run first to see what it would do without doing it. The command is safe to run again: it reports what already exists and re-applies the rest.

platform engineerterminal, in ains-platform
git add ains-orchestrator/targets.yaml docs/targets.md
git commit -m "targets: add AINSPOC"
git push

The running container reads targets.yaml on its next poll, so the project is live within a minute. Add a line to docs/targets.md saying why the project exists.

step3

Optional: the Jira automation rule

platform engineerJira, Project settings → Automation

The command prints a short checklist for a rule that comments on a story when it enters Ready. It is an audit convenience only; the platform works without it.

To take a project off the platform: uv run ains target remove <repo> deletes the target entry and the platform's labels, environments and protection; add --delete-repo only if the repository itself should go.

6Delivering one story

This is the daily path. It is shown with all five gates on. Times are what the sandbox run showed: each agent run takes between fifteen seconds and two minutes, and the orchestrator looks for work once a minute, so a stage normally completes within three minutes of your decision.

step1

Write the story

product ownerJira, the project board
  • Click Create, type Story. Give it a one-line summary (this becomes the PR title and the branch name) and a description that says what should change and how to tell it is done. Two to eight sentences is the sweet spot; the spec agent asks no questions, so what is not written is guessed.
  • Add the label ai-native. Without it the platform ignores the story.
  • Leave it in To Do until you want work to start, then move it to Ready.

You should see within about a minute: the status changes to Specifying by itself and a comment from the platform appears under the story.

step2

The specification is written

orchestrator + spec agentautomatic

The orchestrator makes a copy of the repository, creates the story's branch, and starts the spec agent with your story text. The agent writes specs/<KEY>/spec.md. The orchestrator commits it, opens a draft pull request titled with the story key and summary, links the PR under the story, sets the status to Spec Review and comments with what to do next.

gateG1

G1, approve the specification

product ownerJira, with the PR open in another tab
  • Open the PR link from the story's comment. Click the Files changed tab and read specs/<KEY>/spec.md. Ask: is this what I meant?
  • Yes: in Jira, move the story to Planning.
  • No: write a comment on the story saying what is wrong or missing, then move it to Rework. The newest comment is handed to the spec agent and it rewrites the spec. The story comes back to Spec Review.
step3

The plan is written

orchestrator + plan agentautomatic

The plan agent reads the spec and writes plan.md (how it will be built) and tasks.md (a checklist of concrete tasks) next to it. Both are committed to the same PR. Status becomes Plan Review.

gateG2

G2, approve the plan

product ownerJira, with the PR open
  • Read plan.md and tasks.md under Files changed. Check the scope: nothing missing, nothing extra.
  • Yes: move the story to Implementing.
  • No: comment, then move to Rework. The plan agent runs again with your comment.
step4

The code is written, tested and reviewed

implement agent, CI, review agentautomatic
  • The implement agent works through tasks.md, ticking each task, writing code and tests, and running the tests until they pass. It cannot commit or push; the orchestrator commits what it left and pushes.
  • The PR is marked ready for review. That starts the CI workflow, which installs the project, lints it and runs the tests. The result shows on the PR's Checks tab as ci / ci. CI also moves the story to Code Review.
  • The review agent reads the diff and the CI result with read-only permissions and posts a review on the PR, starting with [ains review agent]. It can comment or ask for changes; it can never approve or merge.

You should see on the PR: new commits, a green or red check, and a review from the orchestrator account. In Jira: Code Review.

gateG3

G3, approve the code

reviewerGitHub, the pull request
  • Checks tab: ci / ci must show a green tick. A red cross next to an older commit in the Conversation tab is history; what counts is the newest commit.
  • Conversation tab: read the agent's review. Files changed tab: read the code if you want to.
  • Yes: in the right sidebar click the gear next to Labels and tick g3-approved.
  • No: write what should change as a comment at the bottom of the Conversation tab, then add the label g3-rework. The implement agent runs again with your comment, pushes, CI runs, the review agent reviews, and the PR waits for you again.
  • CI is red: do nothing. The orchestrator sends the failed test output back to the implement agent by itself, up to two rounds. After that the story goes to Blocked with a comment, and a person has to look.

Why a label and not the Approve button: GitHub does not let an account approve a PR it opened itself. On a single-account setup the label carries the same meaning. Projects with a separate orchestrator account can use --approval-mode review and the normal Approve button instead.

step5

Merge and build

orchestrator, release workflowautomatic

On its next poll the orchestrator sees the label and the green check, squash-merges the PR (all the story's commits become one on main), comments in Jira with the PR link, and deletes its working copy. The merge starts the release workflow, which builds the container image, pushes it to the registry, and then stops to wait for G4.

You should see: the PR badge turns purple, "Merged". Under the repository's Actions tab a run named release with a yellow status.

gateG4

G4, approve staging

release approverGitHub, Actions tab
  • Open the release run. A yellow banner says a deployment is waiting for review. Click Review deployments, tick staging, optionally leave a comment, click Approve and deploy.
  • The image is tagged staging. The workflow moves the story to Staging in Jira and comments with the run link.
  • To stop the release: click Reject instead. The run ends and the story stays where it is.
gateG5

G5, approve production

release approverGitHub, the same run

The same run pauses again. Review deployments, tick production, Approve and deploy. The image is tagged production and the story moves to Done.

The story's comments now hold the whole trail: every claim, every agent run, every gate decision, the PR link and the release run link.

A story that does not need all this: switch gates off for the project (section 7). An off gate is passed automatically and the platform leaves a comment saying so, so the trail never has a silent skip.

A pull request a person wrote

Developers can keep working the ordinary way. Add the label ai-review to any PR in an onboarded repository and the review agent reviews it once per new commit. Merging it is still a human decision; nothing else changes.

8The four agents

Each agent is a fresh, headless run of Claude Code inside the orchestrator's container, with a prompt the orchestrator renders from a template, a turn limit, a wall-clock limit of 30 minutes, and a permission file that lists what it may run. It receives only the subscription token; no API key can reach it. If a run fails, the orchestrator retries once after five minutes, then marks the story Blocked.

AgentReadsProducesAllowed toNever
specthe story, CLAUDE.mdspecs/<KEY>/spec.md via /speckit-specifyedit files (max 30 turns)commit, push, browse the web
planspec.mdplan.md, tasks.md via /speckit-plan, /speckit-tasksedit files (max 30 turns)commit, push, browse the web
implementtasks.md, the repositorycode and tests, ticked tasksedit files, run tests and the linter (max 80 turns)commit, push, edit workflows or settings, add secrets
reviewthe diff, CI result, spec and plana PR review with a verdict line: comment or request changesread, run tests (max 25 turns)edit, approve, merge

The prompts live in ains-orchestrator/agents/stages/ and the limits in agents/claude-code.yaml. Rework hands the agent the human's comment under a heading "Rework requested by the reviewer"; a CI failure hands the implement agent the failing step's output.

10When something goes wrong

You seeWhat it meansWhat to do
Story stays in Readythe platform did not claim itCheck the label ai-native is on the story and the project is in targets.yaml; on the laptop, docker compose ps must show the container healthy
Story is Blockedan agent failed twice, or CI failed three timesRead the comment. Fix the cause (often the story text or a broken test), then move the story to Ready. It resumes at the stage that failed, not from the start
Red ci / ci on the PRtests or lint failedNothing at first: the platform reworks it. If it is red after the second round, the story will be Blocked; see above
Nothing happens after a label or status movethe poll has not run yetWait one minute. Then check the container log
Agent review says it could not run somethingthe project's .claude/settings.json does not allow that commandPlatform engineer adds the command to the allow list in the template and the project
"requires approval" in the container logsame cause as abovesame fix
Release run waits but you did nothingany push to main starts the release workflowApprove, or Cancel workflow on the run; without a story key it moves nothing in Jira
Token expired or revokedJira, GitHub or Claude calls fail in the logMake a new token, put it in .env, run docker compose up -d
Two things the platform refuses by design: merging a PR without a human approval and a green check, and running an agent with an API key. If you ever need either, it is a change to the platform, not a setting.

11Command sheet

All run on the laptop, in ains-platform/ains-orchestrator.

# container
docker compose up -d --build          # build (after code changes) and start
docker compose ps                     # is it healthy?
docker compose logs -f orchestrator   # live log; Ctrl+C to stop watching
docker compose stop orchestrator      # pause the platform

# health and projects
docker compose exec orchestrator ains doctor
uv run ains targets list
uv run ains target add <repo> <KEY> "<Jira name>" [--gates ...] [--approval-mode label|review] [--dry-run]
uv run ains target remove <repo> [--delete-repo]

# one story
docker compose exec orchestrator ains session status <KEY>    # stage, PR, every event
docker compose exec orchestrator ains session dispatch <KEY>  # claim a Ready story now, without waiting for the poll
docker compose exec orchestrator ains session advance <KEY>   # run exactly one step now

A worked example of every step above, with the problems met and fixed on the way, is the sandbox story AINSSB-2 in docs/implementation-log.md.
